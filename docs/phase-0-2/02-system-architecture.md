# Phase 0 — 系统架构设计

## 1. 总体架构

```text
数据来源层
  Amazon Best Sellers / Movers & Shakers / Search Results / Product Detail
        ↓
采集与落地区
  调度、限流、重试、原始响应留存、批次审计
        ↓
数据处理层
  解析、规范化、验证、去重、品类映射、品牌归一
        ↓
数据库层
  主数据 + 追加式历史快照 + 派生指标 + 信号 + 运行审计
        ↓
分析模型层
  产品追踪、品牌情报、趋势、Opportunity Score、Listing/评论、生态图谱
        ↓
报告输出层
  每日 Markdown 报告 + Daily Ranking 等逻辑视图/导出表
```

质量门禁位于数据处理层和数据库层之间。未通过校验的批次进入隔离区，不更新面向分析的有效数据集。

## 2. 分层职责

### 数据来源层

使用统一 `source_definition` 描述市场、入口类型、品类、搜索词、目标数量和启停状态。搜索排名必须绑定具体搜索词和查询参数；否则“Top 50”没有可比较意义。

### 采集与落地区

每次运行创建唯一 `collection_run`。原始载荷先落地并记录内容指纹，再解析入库，从而支持失败重放、解析器升级和审计。具体采集方式、合规策略、频率与限流参数留待确认后评估。

### 数据处理层

通过稳定的数据契约输出规范记录；校验 ASIN、数值范围、货币、来源、品类映射和必需字段；对标题、品牌、卖家做原值保留加规范值映射。

### 数据库层

将相对稳定的产品/品牌/品类主数据与每日变化的排名、Offer、Listing 和指标快照分离。历史表仅追加。派生字段能够由历史快照重算，但保存计算结果和规则版本以便审计。

### 分析模型层

分析任务只读取已通过质量门禁的完整市场日数据。Opportunity Score 和信号规则采用版本化配置；AI 分析必须晚于确定性指标计算。

### 报告输出层

生成 `Amazon_US_Market_Report_YYYY-MM-DD.md`，并把 Daily Ranking、New Product Entry、New Brand Tracker、Rising Products、Trend Analysis 作为数据库视图或导出工作表提供。

## 3. Category Independent Architecture

核心流水线只处理统一维度：`marketplace + category_id + source_id + product_id + observed_at`。品类差异由以下配置驱动：

- 品类树及父子关系；
- Amazon 外部节点与内部规范品类的映射；
- 配件类型映射；
- 采集入口、搜索词和目标数量；
- 品类专属解析/验证规则（仅在确有必要时作为插件）；
- 报告中的显示顺序与分组。

新增 Generator 等品类时，只增加配置、映射及必要的适配器测试，不修改数据库核心实体、趋势逻辑或报告管线。

## 4. 可靠性与可观测性

- 幂等键阻止同一批次重复写入。
- 每阶段记录输入数、输出数、拒绝数、耗时和错误摘要。
- 原始数据指纹、解析器版本、规则版本关联到输出。
- 单一品类失败不阻塞其他采集任务，但 Data Merge 依据完整性策略决定是否进入分析。
- 报告显示数据新鲜度、覆盖范围和质量警告。

## 5. 安全与合规边界

后续采集设计应在实现前确认 Amazon 适用条款、robots/访问限制、账户和 API 使用方式；凭证只通过密钥管理或环境注入，不进入代码库、日志或原始载荷。当前架构不预设绕过访问控制的实现。

## 6. 部署边界（待确认）

数据库引擎、任务调度器、对象存储、部署环境、告警通道和成本预算尚未指定。本设计用抽象接口隔离这些选择，Phase 3 开工前需形成 ADR（架构决策记录）。
