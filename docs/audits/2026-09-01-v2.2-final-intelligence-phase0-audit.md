审计范围：数据有效日、页面市场上下文、信号生成、市场隔离、缺失/失败规则、优惠显示、缓存与趋势历史。
约束：不改采集器、不重写历史快照、不新增 D1 表。

- 三个独立 Amazon 榜单源保持不变：高压清洗机 `552856`、污水泵 `680335011`、高压清洗机配件 `3023451`。
- 本地历史覆盖 2026-08-12 至 2026-08-31。08-19 是 0 条、三榜均 `NOT_COLLECTED` 的真实失败日；08-25 的失败状态文件保留，但随后生成了精确 3×Top30 的修复 bundle，是否进入线上有效日由 D1 `category_days.complete` 与精确 Top30 校验共同决定。

## 市场上下文与隔离

- `market-context.ts` 已把 URL 作为页面本地 category/segment/date 的来源，并把 cache key 定义为 marketplace/category/segment/date/window。
- 高压清洗机 Raw Top30 与 Analytical machines 已分离；machines 只允许 electric/gas/cordless。配件使用独立 category，不允许从高压清洗机榜单回退。
- 页面大多通过 `buildAnalyticalCategory` 共享筛选，但 Market 页会用 window 重建 comparison 后再次生成信号，造成与 Overview/Alerts/Reports 计数漂移。
- `loadLiveDashboard` 在任意 D1 异常时回退 seed；有显式回退提示，但分析页面仍需确保不会跨市场借用数据。

## 信号与报告

- `ui-intelligence.ts` 的主要信号仍是 `high/watch/entry/activity` 四级；普通新入榜使用 `entry`，Top10 新入没有被提升为 High。
- `seller-intelligence.ts` 另行生成 `high/medium/low` 信号，普通 Top30 entry/exit 被标为 High；这是重复计算和跨页面计数不一致的根因。
- 现有去重依赖生成路径互斥，没有显式的 product+date+event 去重与同事件最高等级规则。
- Reports 页面仍以旧工作台入口和 PDF 归档为中心，未按摘要→High→Watch→Activity→Evidence→Methodology 的顺序统一展示 canonical signals。

## 缺失值、优惠与缓存

- 数值读取会把无效值归一为 `null`，基础格式函数以 `—` 显示缺失值，未把缺失值写成 0。
- 当前优惠只依据 `has_discount` 与字符串数组格式化，没有 current price、reference price、discount >= 0 的统一显示校验器；可疑值无法统一显示“优惠信息待确认”。
- 未发现额外的服务端内存缓存；HTTP cache 为 300 秒，客户端请求已含 category/segment/date。趋势窗口仍需加入统一 query/analysis key 并做反序测试。

## 趋势、产品与品牌

- Products 只有 1D、价格、评论和恒定“Top30 在榜”；缺少 7D 与有效日 Presence。
- Market 的 7D/30D 基线是单日索引，不是“当前窗口 vs 前一等长有效日窗口”，历史不足也会取最老日，结论不可靠。
- Brands 只有上一有效日席位变化；`buildBrandStructure` 把 Others 与 Unknown 合并，且 Unknown 可能进入扩张/收缩语义。
- 首页已有模板摘要雏形，但未使用统一 Daily Brief 合同。

## Gate 决策

Gate A 必须先建立唯一 Signal Engine、三等级、显式去重、失败日保护、优惠显示校验和完整 cache key；随后 Gate B 才能让 Reports/Alerts、Products、Market、Brands、Overview 消费同一合同；最后 Gate C 统一格式、日期回落提示、Methodology 与空状态。数据库 schema 足以支持本 PRD，不执行迁移。
