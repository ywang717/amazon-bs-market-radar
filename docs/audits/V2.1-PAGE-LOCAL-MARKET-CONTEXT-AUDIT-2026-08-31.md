## Existing Context Architecture

- `web/lib/catalog.ts` already owns the three authoritative category-to-node mappings.
- `web/lib/market-context.ts` already validates API contexts and filters product metadata, but uses one global default and lacks page defaults, URL normalization and independent accessory subsegments.
- `/api/public/overview` and `/api/public/rankings` already accept `category` and `segment` and keep the independent accessories category separate from Pressure Washers.
- Page components do not derive their data from URL context. Most select `pressure_washers` directly and call `buildAnalyticalCategory` with its implicit Machines default.
- `MarketContext.tsx` is presentation-only; it has no category/segment controls or URL updates.
- There is no global mutable market store or localStorage synchronization, which is a safe base for page-local state.

## Hard-coded Category Locations

- `web/app/page.tsx`, `market/page.tsx`, `products/page.tsx`, `brands/page.tsx`, and `insights/page.tsx` select Pressure Washers directly.
- `web/app/components/ShellNavigation.tsx` fetches the Pressure Washers / Machines overview and reads Pressure Washers coverage for both drawers.
- `web/app/reports/page.tsx` links Alerts to `category=pressure_washers`; `ReportsArchive.tsx` loads every category.
- `web/app/rankings/page.tsx` renders all three raw groups instead of one page-local context.
- `web/lib/ui-intelligence.ts` has a legitimate Machines default that becomes unsafe when callers omit an explicit page context.
- Seller Intelligence accepts a category but not a segment; the page URL and links do not preserve the full market context.

## Existing URL Handling

- Market preserves `view` and `window`, but not category/segment.
- Analysis parses `workspace`, `profile`, `category`, `date`, `report`, and alert priority independently.
- Product detail links do not carry their source context and the back link always returns to an unscoped Rankings page.
- Primary navigation drops all context. Refresh and deep links therefore cannot currently restore most page selections.

## Cache Risks

- No React Query, SWR, global market store, or shared derived-metric cache exists.
- Client fetch state in `ShellNavigation`, `ReportsArchive`, and `AnalysisCenter` is not keyed by category/segment and can display stale data after a URL change.
- Server pages are dynamic, so the main isolation requirement is to pass context into every loader/derivation and include it in client effect dependencies and request URLs.

## Cross-market Data Risks

- Overview, Market, Products, Brands, and Data Status always publish Pressure Washers metrics regardless of the visible desired market.
- The Data Status drawer reads Pressure Washers rows even when opened from another page context.
- Reports and Alerts can mix categories in lists or lose the source market during navigation.
- Rankings currently preserves independent raw sources correctly, but the UI does not enforce one selected market or analytical segment.

## Reusable Components

- `MarketContext`, `ProductIdentity`, `RankDisplay`, `SignalCard`, `EmptyState`, and current tables/cards remain reusable.
- `loadLiveDashboard`, `loadAnalyticalOverview`, `buildAnalyticalCategory`, signal builders, brand aggregation and public routes already provide the required data primitives.
- Existing category config, classification rules, Amazon nodes, D1 schema and crawler must remain unchanged.

## Required Changes

1. Extend the single market config with page defaults, labels, segment resolver, parser and serializer.
2. Make URL context authoritative and normalize invalid/missing pairs without losing page-local parameters.
3. Turn `MarketContext` into accessible category/segment controls that update only the current URL.
4. Add context-preserving navigation while keeping each browser tab independent.
5. Pass the resolved context explicitly through every core page, drawer fetch, report filter, product link and analytical builder.
6. Key all client fetch state by category/segment and verify independent Accessories always uses node 3023451.
7. Add unit, rendered integration, browser navigation, multi-tab, responsive and production QA.
